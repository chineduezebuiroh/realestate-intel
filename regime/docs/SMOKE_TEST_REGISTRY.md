# Smoke Test Registry v1

## A. Purpose of the smoke-test suite

The numbered smoke-test suite under `scripts/smoke_tests/` is the repository's executable contract layer for regime-pipeline behavior. It protects configuration loading, feature construction, scoring, alignment, artifact IO, diagnostics, and experiment-review workflows with small synthetic fixtures, production-like integration runs, and artifact schema/content checks. The suite is intentionally broader than unit tests: many scripts validate business contracts such as no partial structural-window emission, canonical source lineage, chronology-review reproducibility, and production-readiness acceptance.

This registry inventories the 56 discovered numbered Python scripts (`00` through `55`) and records what each test actually protects based on script contents, imported implementation modules, assertions, artifact writes, and run behavior.

## B. Test category definitions

- **unit-like synthetic contract**: Builds small in-script fixtures and checks deterministic formulas, schemas, error handling, or edge cases without requiring prior artifacts.
- **integration**: Exercises multiple regime pipeline stages or real repository configuration/data through production modules.
- **artifact contract**: Validates artifact store manifests, expected files, hashes, schemas, or reproducible generated outputs.
- **regression**: Locks previously accepted behavior, aliases, immutable outputs, or backwards compatibility.
- **diagnostic/audit**: Produces or validates analytical summaries used by reviewers; may focus on ranges, non-emptiness, grain uniqueness, or flags rather than exact values.
- **end-to-end**: Runs a substantial pipeline or acceptance path across source metrics, feature/scoring layers, artifact persistence, and review outputs.

## C. Rules for adding or extending smoke tests

1. Extend an existing numbered test when the new assertion protects the same contract, stage, and failure interpretation.
2. Add a new number only for a genuinely distinct contract or execution layer that cannot be expressed as a parameter in an existing test.
3. Keep source-controlled fixtures small and deterministic; generated review artifacts belong under `artifacts/` unless they are intentionally frozen fixtures.
4. Every smoke test should fail with actionable `AssertionError` messages; diagnostic-only print scripts should be upgraded when touched.
5. If a script writes artifacts, use a unique output directory or clean the target directory before writing.
6. Prefer synthetic unit-like fixtures for formula contracts and integration/artifact tests for chronology, adjudication, and production acceptance.

## D. Numbering and naming conventions

- Numbers are two digits and increase in rough pipeline/evolution order.
- Directory bands (`00_09`, `10_19`, etc.) mirror the numeric prefix.
- Names should identify the protected contract, not just the implementation module.
- Missing numbers are allowed, but this v1 inventory found no gaps from `00` through `55`.
- Superseded tests should remain documented until removed or consolidated.

## E. Generated artifacts versus source-controlled fixtures

- Generated smoke outputs should be written under `artifacts/regime/...` or a clearly named `_smoke_test` subtree, not under `config/` or production source directories.
- Source-controlled fixtures should be small, stable inputs needed to reproduce contract assertions.
- Review CSV/JSON outputs are evidence artifacts and should be regenerated, not hand-edited.
- Artifact writers must avoid shared directories unless the script intentionally validates a shared end-to-end run.

## 1. Dependency and execution map

### Major groups and rough ordering

1. **Core pipeline stage smokes (`00`-`09`)**: config, feature, normalization, metric, alignment, dimension, axis, coordinate, geometry, and assignment stages. These are conceptually sequential and are useful first failures, but most scripts call their stage directly rather than consuming a file written by the preceding smoke.
2. **Validation and artifact foundations (`10`-`19`)**: trajectory/transition/seasonality/contribution diagnostics, permit traces, artifact IO, pipeline runner, and early experiment comparison checks. Smoke `15` is the artifact-store contract; `16` is the first broad end-to-end runner/artifact check.
3. **Diagnostics and smoothing foundations (`20`-`29`)**: derived-lineage/freshness, chronology, contribution/volatility/transition diagnostics, smoothing policy, and generic smoothing formulas. `28` defines smoothing-registry expectations; `29` validates generic smoothing formula mechanics.
4. **Inventory and source-family experiments (`30`-`39`)**: canonical source metrics and active-inventory comparisons, smoothing overrides, inventory chronology/window diagnostics, price-family source diagnostics, and early linked price-family recalculation.
5. **Demand/labor and linked price-family experiments (`40`-`50`)**: linked price-family features/comparison, demand contribution diagnostics, labor source/comparison/chronology/readiness, and immutable LAUS MA6 acceptance.
6. **Price-family Phase 1/2 structural linked suite (`51`-`55`)**: MA12 structural feature contract, linked-derived recalculation, chronology review, stability/seasonality review, and integrated Phase 2 review.

### Artifact-consuming relationships

- `15_artifact_io.py` writes and verifies `artifacts/regime/_smoke_test`; it is isolated and should not be used as input by later tests.
- `16_pipeline_runner.py` validates pipeline and validation artifacts through `RegimeArtifactStore`; later comparison tests may rely on production-like artifacts but do not have a hard dependency on `16` being run in the same session.
- `50_laus_ma6_immutable_acceptance.py` consumes artifact-store runs and writes `artifacts/regime/comparisons/laus_ma6_immutable_acceptance`.
- `51` and `52` write Phase 1 evidence under distinct subdirectories of `artifacts/regime/comparisons/price_family_structural_windows`; Phase 2 tests now write candidate-isolated evidence for MA6, MA9, and MA12 under the shared structural-window comparison root.
- `53` writes/validates `phase2_chronology`; `54` writes/validates `phase2_stability_seasonality`; `55` requires chronology and stability artifacts as inputs and validates integrated `phase2_review` outputs.

### Hard dependencies versus conceptual relationships

- **Hard dependencies**: `55` expects the Phase 2 chronology and stability/seasonality input artifacts named by `price_family_phase2_diagnostics`; `16` requires named pipeline/validation artifacts; artifact acceptance tests require artifact-store manifests and files.
- **Conceptual relationships**: numeric ordering from `00` to `14`, source diagnostics before comparison reviews, and Phase 1 formula tests before Phase 2 review tests are conceptual. Most scripts rebuild their own frames or invoke modules directly and do not literally read a previous smoke-test output.
- **Hidden execution-order risk**: tests that write shared experiment directories (`36`, `45`, `47`, `48`, `50`, `53`, `54`, `55`) can overwrite previous generated review evidence. `53`/`54`/`55` intentionally share the same price-family comparison root, so the expected order is chronology and stability generation before integrated review validation.
